## Closed since this audit

**Gap 1 (L1) — partially closed, 2026-10-03.** The 前十名股东 / 前十名流通股东 tables are
now read from the Eastmoney relay rather than the PDF text layer, which cannot
reconstruct them (`cninfo_disclosure.py` refuses them explicitly because the headers split
and the values lose column binding). New families `shareholders_top10` /
`shareholders_free_float`; units verified against published ground truth (600519 rank-1
681,282,935 / 1,250,081,601 = 54.4999% vs published 54.5, and the same on 000001, 688111,
300750); no sum or concentration ratio is derived, so no ledger row is owed.

**Gap 1b (L1) — closed 2026-10-03.** The 限售股份变动情况 table (per-holder 年初/本年解除/本年增加/
年末 restricted shares, with 限售原因 and 解除限售日期) is now read out of the periodic report body by
`mira_data fetch lockup_change <code>`. Which extractor to use was measured, not assumed: the plain
text layer destroys the table; layout mode keeps rows on one line but still glues adjacent cells in
the 合计 row; and coordinate clustering emits each visual row as *two* clusters ~0.6pt apart, so no
single row-band tolerance can merge them without also merging the neighbouring row. Layout mode won
because the data rows are space-separated — with the issuer's own published 合计 row as a
**mandatory** checksum, so "no readable 合计" is a refusal rather than an unvalidated emit. That rule
earned its place immediately: the first working draft read the four numeric columns right-to-left
and produced opening=0 / added=649,900,000 for a row the filing states as opening=649,900,000 /
added=0, and only the checksum caught it. Verified against 海光信息 FY2025 (six holders,
1,437,780,910 shares released), matching that issuer's standalone 限售股上市流通公告 for the same
event.

All three fields the L1 review named are therefore covered: 股东户数 from the body, the two
shareholder tables from a relay, and the restricted-share movement from the body.

**Gap 2 (L1) — the index was wrong, but the coverage gain is smaller than it first looked.**
The original entry here said "probe-exhausted / needs a browser-grade renderer". That was wrong
about the *mechanism*: the portal has two indexes, and every earlier probe had queried only the
announcement feed. `POST /new/fulltextSearch/full` (public, keyless) does carry
投资者关系活动记录表, and `mira_data fetch ir_activity` now falls back to it.

**But the Shenzhen gain is marginal, and measuring it changed the conclusion.** A sample of 16
large Shenzhen names (000001, 000002, 000333, 000651, 000725, 000858, 002230, 002352, 002415,
002475, 002594, 300059, 300124, 300308, 300750, 300760) returns **zero** IR-activity records in
2025-01..2026-10 from *either* index. 宁德时代 (300750) has no IR record in its first 1000 search
hits. And inside the index's own IR corpus the market split is lopsided: for 2026-07..09 the
Shenzhen share was 3 records out of 44 (7%), against 29 Shanghai and the rest HK-line copies.

So the honest status is **open, with a narrow exception**: the search index carries a handful of
Shenzhen names (301277, 002486, 002573, 002921, 301584, …) and the 5-digit HK-line 海外监管公告
copies, while the bulk of Shenzhen remains absent — as do 美力科技 (300611) and 科大国创 (300520),
whose records are publicly readable but in neither index. Do not read the fallback as "Shenzhen is
covered".

The wrong-index error is still worth keeping, because one of the probes it rested on was itself
broken: the 互动易 platform search **ignores its keyword** (a nonsense key and a real one return
identical `totalRecord` 62829 and the same first row), so the old conclusion "there is no survey
document type in that index" never had support. And `pageSize` on the search endpoint is silently
capped at 100.

A route that would actually close this was mapped and set aside: `dataclouds.cninfo.com.cn/shgonggao/`
is an S3-style bucket with a public date listing (`investor/{year}/{yyyymmdd}/{hash}.PDF`,
~19-77 docs/day) whose PDFs print `股票代码` on page 1. It has no code→document index, so it needs
a full-corpus crawl, and Range requests do not work (pypdf needs the trailing xref, so any
truncation fails to parse). That is a cost decision, and it is the only route found that would
cover the Shenzhen bulk.

## Also fixed: the 8 validator errors

Independently of the gap above, the repo's `just check` was failing with **8 errors** from an
untracked `analysis/688008-2026-10-02/` scratch directory: a non-canonical evidence-log header
and a research-package manifest in a pre-schema shape (`manifest_version: "1"`, no
`package_type` / `hero_artifacts` / `support_artifacts` / `source_scope`).

That directory turned out to hold a **complete, substantive research package** for 澜起科技
(688008.SH / 06809.HK) with no tracked case anywhere in the repo, so it was migrated rather
than deleted or exempted:

- moved to `cases/688008-2026-10-02/` so it is a real case, not an orphan scratch dir;
- `evidence-log.csv` re-expressed from its case-local `claim_id`/`source_ref` columns into the
  canonical **v1.2** header, 58 rows, with `derived_calculation`/L6 rows carrying
  `upstream_sources` + an explicit `Formula:` (no `calculation-ledger.csv` exists, so the
  formula note is the reproducibility path). No claim, figure, date or judgment was changed;
- manifest rebuilt to `mira_research_package_v1` with the required fields, preserving the
  case's own `blocking_gaps`, `must_refresh_if` and `stale_after: 2026-10-31`;
- `routing.json` added and verified against `schemas/routing.schema.json` (the case was
  migrated into `cases/`, which makes the routing card mandatory for any case holding a memo
  or evidence log);
- `raw/`, `pdftext/`, `pdftext_via_toolkit/` and `_pylibs/` gitignored by a new
  `cases/*/<payload>/` rule — vendor JSON, third-party filing text and a vendored library stay
  local, so only ~0.15 MB of readable artifacts is tracked.

Result: `scripts/validate_repo.py` **0 errors** (was 8) and `scripts/run_quality_gate.py`
passes, 29/29 checks.

## Independent confirmation from a real case

`cases/688008-2026-10-02` (澜起科技, built 2026-10-02 before this channel existed)
reaches the same structure by hand and its numbers reconcile with the new channel:

| case memo (2026-06-30) | channel (2026-07-23, the later filed period) |
| --- | --- |
| WLT Partners 3.68% | 3.6879% |
| 上海融迎 2.10% | 2.1038% |
| 陆股通 / 香港中央结算 11.93% | 11.43% |
| "前十大股东里有 5 只被动指数 ETF" | 4 STAR50/chip ETFs + the buyback account, visible by name |
| "无控股股东，无实际控制人" | no holder above 11.5%; largest is the HK clearing nominee |

The channel also separates **流通A股** from **流通H股** — for a dual-listed issuer the
H-share line appears as `HKSCC NOMINEES LIMITED` 6.21% in the same top-ten table, so merging
the two share classes would have double-counted the depositary structure. That is why the two
tables are never merged and each percentage carries its own `ratioField` / `ratioBasis`.
